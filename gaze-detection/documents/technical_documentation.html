01 Overview

A gaze-tracking system that estimates where a user is looking on their screen using only a standard laptop webcam — no infrared illuminators, no depth sensor, no head-mounted hardware.

The system solves three problems in sequence:

  1. Where is the face, and where is it in 3D space? — MediaPipe landmarks + pinhole distance estimation.
  2. Which direction are the eyes pointing? — L2CS-Net gaze model.
  3. Which screen pixel does that direction correspond to for this user? — per-person polynomial calibration.

A positioning gate constrains the user to a fixed region of space so step 3 remains valid, and a self-improving data loop collects labeled training samples during normal use.

Canvas ↔ physical scale (development display, 34.4 × 19.4 cm): 37.2 px/cm horizontally, 37.1 px/cm vertically — near-identical, so pixel radii translate to centimetres uniformly.

Angles: gaze pitch/yaw are in radians everywhere after decoding. Positive yaw = subject looking to their right in the mirrored view; positive pitch = looking up. Head pose is in degrees.

04 Algorithms

4.1 Face and iris landmarks

MediaPipe FaceLandmarker (Tasks API, face_landmarker.task) in RunningMode.VIDEO, num_faces=1, detection/tracking confidence 0.5. Video mode requires monotonically increasing timestamps; the pipeline synthesizes them as frame_idx × (1000/30) ms.

IndexAnatomyConsumer
468Left iris centerDistance (IPD), iris features
473Right iris centerDistance (IPD), iris features
1Nose tipCentering check
33, 133, 362, 263Eye cornersIris ratio, EAR
234, 454, 10, 152Face extentsFace width / height
0–477AllGaze-model crop bbox
Capture resolution is functionally significant. The sensor is natively 16:9 at 1280×720. Requesting 640×480 causes the driver to center-crop to 4:3, narrowing the effective horizontal field of view. This invalidates the assumed focal length (biasing all distance readings closer than reality) and halves the pixel count across the iris.

4.2 Head pose

Enabled via output_facial_transformation_matrixes=True. The 4×4 matrix is computed by MediaPipe from its full internal 3D face model. Rotation extracted with SciPy:

rotation = np.array(transformation_matrix)[:3, :3]
pitch, yaw, roll = Rotation.from_matrix(rotation).as_euler('xyz', degrees=True)
tx, ty, tz = np.array(transformation_matrix)[:3, 3]
Rationale. A hand-rolled 6-point solvePnP was replaced because exact anatomical 2D↔3D correspondence is easy to get subtly wrong on a mirrored frame, which produced errors on the order of 60° yaw / 170° roll while the subject faced forward.

4.3 Distance estimation (monocular, known-size)

The same principle a camera-only vehicle uses to judge distance: project an object of known real-world size and measure its apparent size. Our known object is the interpupillary distance (IPD).

distance_cm = focal_px · REAL_IPD_CM / ipd_px ipd_px = ‖(landmark₄₇₃ − landmark₄₆₈) ⊙ (W, H)‖₂

Focal length resolution order:

  1. Measured (preferred) — calibrate_focal() at a known distance: focal = ipd_px · known_dist_cm / REAL_IPD_CM, persisted to models/camera_focal.json, linearly rescaled if capture width changes. Measured value on this machine: 1073.4 px.
  2. Estimated fallback — focal = W / (2·tan(HFOV/2)). At W = 1280, HFOV = 60° → 1108.5 px.

in_zone = (MIN ≤ d ≤ MAX) ∧ (|dx| ≤ TOL) ∧ (|dy| ≤ TOL) RED = ¬in_zone YELLOW = in_zone ∧ (near a distance edge ∨ |offset| > 0.7·TOL) GREEN = otherwise

evaluate(landmarks, frame_shape) returns a dict with distance_cm, signed dx/dy, distance_ok, centered, in_zone, zone, and guidance messages. Returns None when IPD is degenerate (< 1 px).

Overlay. Parking-sensor display: discrete level segments spanning 30–80 cm in 5 cm steps (nearest at bottom), allowed band drawn green with yellow warn margins, active segment highlighted; a centre-tolerance box with nose marker; directional guidance; and a border flash whose frequency scales 2 → 8 Hz with the magnitude of violation.

Enforcement contract. Every consumer discards gaze data while in_zone is false. This is the mechanism by which the constraint buys accuracy — out-of-position samples are never recorded, so they cannot contaminate the fit.

4.5 Gaze estimation

  • Model: L2CS-Net trained on Gaze360, exported to ONNX, executed on CPUExecutionProvider with intra_op_num_threads = 4.
  • Preprocessing: BGR→RGB, resize 448×448, scale to [0,1], ImageNet mean/std normalization, HWC→CHW, batch dimension.
  • Decoding: two 90-bin logit vectors → softmax → expectation over bin indices → deg = Σ(pᵢ·i)·4 − 180 → radians.
Critical implementation detail. The ONNX graph emits (yaw_bins, pitch_bins) — not (pitch, yaw). Handled in gaze_pipeline._predict_gaze_radians(). Reversing it silently transposes the gaze axes and was a genuine historical defect.

Crop stabilization. The bounding box over all landmarks is converted to a square (side = max extent × 1.3) and smoothed across frames: bₜ = α·b_measured + (1−α)·bₜ₋₁, α = 0.3. Squareness preserves aspect ratio through the 448×448 resize; smoothing prevents crop jitter appearing as gaze jitter. State is module-level and must be cleared via reset_bbox_smoothing().

4.6 Calibration

Phase A — positioning gate

Blocks until zone == "GREEN" is held continuously for HOLD_GREEN_SECS = 2.0; any RED/YELLOW frame resets the timer.

Phase B — smooth-pursuit sweep

A dot traverses a polyline at constant speed while samples are recorded every frame. Path geometry (build_pursuit_path), margin m = 0.05:

  1. Snake: 5 horizontal rows at y ∈ linspace(m, 1−m, 5), alternating direction.
  2. Perimeter: right edge ascent → top edge → left edge descent → bottom edge.
  3. Diagonal: bottom-right → top-left through the centre.

Total: 15 vertices, path length 10.27 screen-units, duration 10.27 / 0.12 = 86 s.

Design rationale. A pure snake only touches each edge instantaneously at a turn, and the settle-time filter then discards the samples immediately following that turn — leaving corners with effectively no training data, so the polynomial extrapolated there. This produced reproducible corner errors up to 6.2 cm. The perimeter pass gives every edge a dedicated slow traversal approached from two directions; measured top-right error fell from 6.2 cm to 0.7 cm.

Sample admission

FilterThresholdReason
Positioning gate in-zonein_zoneConstraint enforcement
Time since direction change≥ 0.3 sEye lags the dot after a turn
Face detected, crop non-empty—Validity

Fit. PolynomialFeatures(degree=3) over the 2 gaze features yields 10 terms — [1, p, y, p², py, y², p³, p²y, py², y³] — feeding two independent LinearRegression models (x and y).

Robust refit. Fit → residual norms → retain samples within median + 2.5·1.4826·MAD → refit on survivors (only if ≥ 60 remain). The 1.4826 factor converts MAD to a normal-consistent σ estimate. Removes blinks and glances away.

Why degree 3. Accuracy degrades when looking downward because the eyelid occludes the pupil, a nonlinearity a quadratic cannot represent. Raising the degree reduced worst-corner error from 8.4 cm to 4.1 cm. With 400+ samples and 10 terms, overfitting risk is low.

Rest interval

A 5 s pause precedes validation. Validating immediately after 86 s of continuous pursuit measurably inflated error (18.3% vs 9.8% of screen) due to ocular fatigue.

Phase C — held-out validation

5 static points (centre + 4 mid-quadrants), each 1.2 s dwell + 1.5 s sampling, median-aggregated. Absent from the training path, so the resulting error is a genuine generalization estimate — unlike fit_error_normalized, which is training-set error and optimistic.

4.7 Drift correction

Problem. The mapping is conditioned on the exact posture held during calibration. A 1–2° difference in head pitch at a later session displaces every prediction by a near-constant offset — diagnosable in the accuracy report as error vectors that are all parallel and equal in length.

drift = predict(median_pitch, median_yaw) − (0.5, 0.5) corrected(x, y) = clamp₀¹( predict(x, y) − drift )

Run at the start of milestones 6/7/8 by sampling gaze at a single known centre point. This is the standard procedure used by commercial eye trackers.

Caveat. Because drift is measured at screen centre, the centre test point in milestone 6 becomes partially self-fulfilling — evaluate quality primarily from edge and corner points.

4.8 Aim assist

ZoneRadiusPhysicalBehaviour
Snap≤ 130 px3.5 cmpull = 1.0 — cursor locks to target centre
Magnet≤ 330 px8.9 cmpull = (330 − d)/(330 − 130), linear fade
None> 330 px—Raw cursor

assisted = raw + (target − raw) · pull. The visible target ring is only 70 px (1.9 cm); the magnet field is deliberately not rendered (revealable with d), so assistance is imperceptible to an observer.

Sizing constraint. ASSIST_RADIUS must exceed the model's typical error (4–6 cm ≈ 150–220 px) or the attractor is never entered. The original implementation used 160 px with a 65% maximum pull — it could neither reach the cursor nor fully land it, which is why it appeared non-functional.

4.9 Fixation detection & data integrity

Threat model. Aim assist moves the cursor onto the target regardless of where the user is actually looking. Deriving training labels from the assisted cursor would let the assist manufacture its own ground truth, poisoning the dataset.

Countermeasure. Labeling consults raw gaze only. A sample is admitted when is_fixating() holds:

ConditionThresholdPurpose
≥ 3 samples spanning the hold window0.25 sSufficient evidence at 8–15 fps
Spatial spread≤ 120 px (3.2 cm)Distinguishes fixation from saccade
Centroid distance to target≤ 420 px (11.3 cm)Rejects looking elsewhere entirely
Why stability rather than proximity. Gating on closeness to the target would admit only samples where the model is already correct, from which nothing can be learned. Rows where the model is currently wrong but the eye is demonstrably fixating carry the corrective signal.

4.10 Incremental retraining

  1. Append the session's fixation samples to data/gaze_samples.csv.
  2. Load the complete accumulated dataset.
  3. If len ≥ 200, refit with robust_fit_samples at the existing degree.
  4. Carry forward validation_error and position_constraints; record trained_on source counts; persist.
Known ceiling. Pooling sessions without session-aware features degraded training error to 17.7% once eight sessions were mixed: the same (gaze_pitch, gaze_yaw) legitimately maps to different screen points across postures, and a model that cannot see which session a row came from averages contradictory evidence. Resolving this requires position-aware features — the reason the 32-column schema exists.

Why session_id matters. Head posture differs between sittings, so the same gaze angles legitimately map to different screen points across sessions. Without this column a pooled fit averages contradictory evidence. It permits per-session normalization, session-held-out validation, and drift modelling.

Derived feature definitions

Iris ratio. Raw iris pixels confound eyeball rotation with head position. The ratio projects the iris onto the outer→inner corner axis:

x_ratio = ((iris − outer) · (inner − outer)) / ‖inner − outer‖² y_ratio = (iris_y − midline_y) / ‖inner − outer‖

giving 0 at the outer corner and 1 at the inner corner regardless of where the face sits in frame.

EAR. Standard 6-point formula (‖p₂−p₆‖ + ‖p₃−p₅‖) / (2‖p₁−p₄‖) over landmarks (33, 160, 158, 133, 153, 144) left and (362, 385, 387, 263, 373, 380) right.

Schema migration

_migrate_dataset() runs on every write and handles three cases in place:

  1. v1 (6-col) / v2 (9-col) → v3 — remaps pitch→gaze_pitch, yaw→gaze_yaw, x→target_x, y→target_y, distance_cm→pos_distance_cm; tags rows user="legacy".
  2. v3 with old column order → current order — same columns, reordered.
  3. Short source labels → script-named labels.

Unknown layouts are left untouched rather than risk corruption.

Self-documentation. write_data_dictionary() regenerates data/README.md alongside the CSV on every write, so a plain-English explanation of every column always sits next to the data and cannot go stale. inspect_dataset.py prints a runtime summary: row counts by source, users, sessions, feature coverage, and a 3×3 screen-coverage grid.

08 Verification methodology

milestone6_test_accuracy.py measures a 3×3 grid at 5% / 50% / 95% of each axis — including true corners, the hardest extrapolation region. Points are disjoint from both the training path and Phase C validation points.

Per point: 1.2 s dwell (discarded) + 1.5 s sampling (median-aggregated) → drift-corrected prediction → Euclidean error converted to centimetres via the Windows-reported physical display size.

Mean errorClassification
< 1.5 cmExcellent — approaching commercial systems
< 3.0 cmGood — reliable for button-sized targets
< 5.5 cmFair — regions and quadrants only
≥ 5.5 cmPoor — recalibration required

The report additionally diagnoses error topology: edge-dominant error indicates insufficient polynomial flexibility or edge coverage; centre-dominant error indicates postural change since calibration; uniformly parallel error vectors indicate session drift.
