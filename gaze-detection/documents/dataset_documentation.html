gaze_samples.csv — all 39 columns explained

File: data/gaze_samples.csv Schema: v3, 39 columns Rows at time of writing: 6,373 Written by: milestone 4 & 7 only

Every column: what it is, why it exists, how it is calculated, and which file and function produces it. Example values throughout are taken from one real row of the dataset, shown in the orange chips.

01 What one row is

One row = one video frame in which the program knew exactly where the person was looking, because the program itself had drawn the dot they were told to look at.

MEASURED (what the camera saw)   ──▶   LABEL (where the dot was)
   32 feature columns                     target_x, target_y

                    a supervised learning pair
Nothing in this file is a prediction. The label is the stimulus coordinate the program rendered, so it is known exactly. If a model output were ever stored here, every accuracy figure computed from the file would be circular and meaningless.

Columns 1–3 · Metadata Who and what produced this row
01source stringmilestone7_game
What
Which script and activity created the row: milestone4_pursuit (following the moving calibration dot) or milestone7_game (fixating a game target).
Why
The two activities have different characteristics — pursuit is continuous motion across the whole screen, game rows are static fixations at scattered points. Being able to train or evaluate on one only is essential.
How
Passed as a constant by the caller: SOURCE_PURSUIT / SOURCE_GAME.
Where
calibration_utils.py → constants; written by append_dataset()
02user stringasif
What
Who was sitting in front of the camera.
Why
Calibration is per person — eye spacing, face shape and seating height all differ. Mixing two people's rows into one fit produces a model that suits neither. This column keeps them separable.
How
Read from the GAZE_USER environment variable at import time; falls back to "default". Set with $env:GAZE_USER = "name" before launching.
Where
calibration_utils.py → CURRENT_USER
03session_id YYYYMMDD-HHMMSS20260721-110510
What
One identifier per program run. Every row from a single sitting shares it.
Why
The most important metadata column. Nobody sits down in exactly the same posture twice, so the same gaze angles legitimately map to different screen points across sessions. Without this column a pooled fit averages contradictory evidence — measured: training error rose to 17.7% once eight sessions were mixed. It also enables session-held-out validation, which is the only honest way to estimate real-world accuracy.
How
datetime.now().strftime("%Y%m%d-%H%M%S") evaluated once when the module is imported.
Where
calibration_utils.py → SESSION_ID
Columns 4–5 · Label The ground truth — what the model must learn to output
04–05target_x, target_y float, 0–10.788274, 0.670046
What
Where the dot was on screen when this frame was captured. 0,0 = top-left, 1,1 = bottom-right, 0.5,0.5 = dead centre. The example row's dot was 79% across and 67% down.
Why
This is the answer the model is trained to produce from the 32 measured columns. Normalized rather than in pixels so it means the same on any screen size or resolution.
How
Not measured at all — the program chose this position and drew a dot there, so it is exact.
· milestone 4: the moving dot's position along the pursuit path, sampled every frame.
· milestone 7: the static target's position, recorded only while the raw gaze is confirmed to be fixating.
Where
milestone4_calibration.py → phase_b_pursuit()
milestone7_gaze_game.py → play()
Why some points are deliberately never recorded. The 5 validation dots at the end of calibration and the 9 test dots in milestone 6 are excluded from this file on purpose. They are the exam paper — training on them would make every reported accuracy figure a lie.
Columns 6–7 · Feature Gaze angles — the strongest single signal
06–07gaze_pitch, gaze_yaw float, radians−0.283851, −0.232315
What
Which direction the eyes are pointing. Pitch = up/down, yaw = left/right. The example values are −16.3° and −13.3°.
Why
The only column produced by a trained neural network rather than geometry — L2CS-Net, trained on the Gaze360 dataset of thousands of faces. It carries most of the predictive power; every other feature is context that helps interpret it.
How
A square face crop (padded 30%, EMA-smoothed across frames) is resized to 448×448, scaled to 0–1 and normalized by ImageNet mean/std, then run through the ONNX model. It emits two 90-bin distributions rather than two numbers. Each is softmaxed and reduced to one angle by taking the expectation over the bins:
deg = Σ(pᵢ × i) × 4 − 180, then converted to radians.
Where
gaze_pipeline.py → _predict_gaze_radians(), called via predict_gaze_from_crop(). Model file: models/l2cs_gaze360.onnx.
Output order trap. The ONNX graph emits (yaw_bins, pitch_bins) — not pitch first. Reversing it silently transposes the gaze axes and was a real defect in this project's history. Handled inside _predict_gaze_radians(); do not "fix" it back.
Blank in some rows. These two are the only feature columns that can be empty: the gaze model is only run while the positioning gate reports you in position, so out-of-zone frames have no angles. Such rows are not saved anyway.
Columns 8–13 · Feature Head pose — rotation and position in 3D
08–10head_pitch, head_yaw, head_roll float, degrees3.53, −1.15, 4.18
What
How the head is turned. Pitch = nodding yes, yaw = shaking no, roll = ear toward shoulder. The example head was almost straight: tilted down 3.5°, rotated 1.2°, tilted sideways 4.2°.
Why
The same eye angle lands on a different screen point depending on which way the head faces. Recording head pose separately lets a model tell "eyes moved" apart from "head moved" — the two produce identical iris pixel shifts but mean different things.
How
MediaPipe fits its full internal 3D face model and returns a 4×4 transformation matrix. The top-left 3×3 block is the rotation; SciPy decomposes it:
Rotation.from_matrix(m[:3,:3]).as_euler('xyz', degrees=True)
Where
gaze_features.py → head_pose_from_matrix(). Matrix supplied by gaze_pipeline.detect_face(), which requires output_facial_transformation_matrixes=True on the landmarker.
11–13head_tx, head_ty, head_tz float, matrix units−1.34, 1.06, −35.72
What
Where the head sits in space relative to the camera. tz is depth — negative means in front of the camera, and its magnitude tracks distance.
Why
Position, not just orientation. Sitting higher, lower or off to one side changes the geometry between eye and screen even when the head angle is identical.
How
The right-hand column of the same 4×4 matrix: m[:3, 3]. No further processing.
Where
gaze_features.py → head_pose_from_matrix()
Units. head_t* are in MediaPipe's own model units, not centimetres. tz ≈ −35.7 here while the gate independently measured 59.1 cm — they correlate but are not the same scale. Use pos_distance_cm when you need real centimetres.
These can be blank if SciPy is not installed or the matrix is unavailable — head_pose_from_matrix() returns six Nones rather than crashing.
Columns 14–17 · Feature Iris positions in the image
14–17 iris_left_x/y, iris_right_x/y float, 0–10.4368, 0.4145, 0.5259, 0.4019
What
Where each iris centre sits in the camera image. The example's left iris was 44% across the frame, the right 53%.
Why
The raw observation the eye features are built from. On its own it is ambiguous — moving your head shifts these numbers exactly as much as moving your eyes does, which is why the ratio columns exist. Kept because absolute position still carries information about framing.
How
Read directly, no computation: landmarks[468].x/.y and landmarks[473].x/.y. MediaPipe's refined iris model resolves these to sub-pixel precision.
Where
gaze_features.py → extract_features()
Columns 18–21 · Feature Iris ratio — the head-invariant eye direction
18–21 iris_left_ratio_x/y, iris_right_ratio_x/y float, ~0–1 / ~±0.20.5590, −0.0442, 0.3822, −0.0490
What
Where the iris sits inside its own eye. 0 = at the outer (temple) corner, 1 = at the inner (nose) corner, 0.5 = centred. ratio_y is the vertical offset from the corner-to-corner midline.
Why
The best geometric eye-direction feature in the dataset. Because it is measured relative to your own eye corners, it stays the same wherever your head is in the frame and however close you sit — the thing raw iris pixels cannot do.
How
A vector projection of the outer→iris vector onto the outer→inner eye axis, normalized by the eye's width: 
x_ratio = ((iris − outer) · (inner − outer)) / ‖inner − outer‖²
y_ratio = (iris_y − midline_y) / ‖inner − outer‖
Projection rather than a plain (x−x₀)/(x₁−x₀) because the eye axis tilts when you tilt your head; the projection follows the tilted axis, a plain x-ratio silently breaks.
Where
gaze_features.py → iris_ratio()
The two eyes move in opposite numeric directions. The left eye's axis runs left→right in the image (outer #33 → inner #133) while the right eye's runs right→left (outer #263 → inner #362), so both measure the same anatomical direction: temple → nose. The consequence is that looking right raises iris_left_ratio_x and lowers iris_right_ratio_x. In the example row: 0.559 vs 0.382 — both irises physically displaced the same way. Their pattern encodes direction; their difference carries convergence, which relates to viewing depth.
Columns 22–29 · Feature Eye corners
22–29 eye_{left,right}_{outer,inner}_{x,y} float, 0–1 · 8 columns0.4152 … 0.4000
What
The four eye-corner points, x and y each.
eye_left_outer = #33 · eye_left_inner = #133 · eye_right_inner = #362 · eye_right_outer = #263
Why
Three jobs: they define the reference frame the iris ratio is measured against; their separation gives each eye's width (the normalizing denominator); and their positions encode eye shape and how the face is oriented.
How
Read directly from the landmark list, no computation.
Where
gaze_features.py → extract_features(), loop over the four named indices.
Naming. “Outer” always means the temple side and “inner” the nose side — which is why the column order differs between the eyes (left_outer, left_inner, right_inner, right_outer). Reading them left-to-right traces across the face.
Columns 30–31 · Feature Eye openness (EAR)
30–31ear_left, ear_right float, ~0.10–0.350.2983, 0.3033
What
Eye Aspect Ratio — how open each eye is. About 0.30 wide open, about 0.10 shut. The example row's eyes were fully open.
Why
Three uses. (1) Flags blinks, when eye readings are worthless. (2) Captures the drooping-eyelid effect when looking down, which is the physical reason bottom-of-screen accuracy is worst. (3) At runtime it drives the blink-to-click control in milestone 9.
How
The standard six-point formula — two vertical lid gaps averaged, divided by the horizontal width: 
EAR = (‖p₂−p₆‖ + ‖p₃−p₅‖) / (2 × ‖p₁−p₄‖)

left  p₁..p₆ = 33, 160, 158, 133, 153, 144
right p₁..p₆ = 362, 385, 387, 263, 373, 380
Measured in pixels, so it is scale-free: dividing by the eye's own width cancels distance.
Where
gaze_features.py → eye_aspect_ratio()
Columns 32–34 · Feature Face geometry — scale cues
32–33face_width, face_height float, 0–10.1903, 0.4430
What
How much of the frame the face occupies. The example face was 19% of the frame's width and 44% of its height.
Why
A direct proxy for distance — a bigger face means closer. Also useful for spotting a person whose face is unusually large or small in frame, which changes every other pixel measurement.
How
face_width = |landmarks[454].x − landmarks[234].x| (cheek to cheek)
face_height = |landmarks[152].y − landmarks[10].y| (chin to forehead)
Kept in normalized units, so both are fractions of the frame.
Where
gaze_features.py → extract_features()
34ipd_px float, pixels114.485182
What
Interpupillary distance — the straight-line pixel gap between the two iris centres. 114 px in the example.
Why
The single measurement the entire distance estimate rests on, kept raw so a model (or you) can recompute distance under different assumptions instead of trusting the 6.3 cm average.
How
Pythagoras between the two iris points after converting to pixels:
ipd_px = ‖(landmark₄₇₃ − landmark₄₆₈) ⊙ (1280, 720)‖₂
The multiply matters — normalized coordinates are not square, so the distance must be taken in pixel space.
Where
gaze_features.py → extract_features(), using _dist() and _px()
Columns 35–37 · Feature Position — from the positioning gate
35pos_distance_cm float, centimetres59.069595
What
Estimated distance from the screen in real centimetres. 59.1 cm in the example — inside the allowed 45–65 cm band.
Why
Distance changes where a given eye angle lands on screen, so it is essential context. It is also the value the positioning gate enforces — every row in this file was captured within the allowed band, because out-of-zone frames are discarded before they can be written.
How
The pinhole camera model applied to a known real-world size — the same principle a camera-only car uses to judge distance: 
distance_cm = focal_px × 6.3 / ipd_px
6.3 cm is the adult average pupil separation. focal_px is 1073.4 on this machine, measured by sitting at exactly 50 cm and pressing c in milestone 5 (otherwise estimated from an assumed 60° field of view).
Check against the example row: 1073.4 × 6.3 ÷ 114.485 = 59.07 ✓
Where
positioning_gate.py → PositioningGate.evaluate(); copied into the row by gaze_features.extract_features()
36–37pos_face_dx, pos_face_dy float, ±0.5−0.020778, 0.017158
What
How far off-centre the face sits in the frame, as a fraction. 0,0 means perfectly centred; negative dx is left of centre, positive dy is below centre. The example was almost perfectly centred (2% off each way).
Why
Sitting off to one side skews the geometry between eye, screen and camera. Recording the offset lets a model correct for it, and it is the second constraint the gate enforces — beyond ±0.12 the frame is rejected.
How
Nose tip position minus the frame centre:
dx = landmarks[1].x − 0.5   dy = landmarks[1].y − 0.5
Where
positioning_gate.py → PositioningGate.evaluate()
Columns 38–39 · Metadata When and which layout
38timestamp ISO-86012026-07-21T11:05:42
What
When the batch was written to disk — not when the individual frame was captured. Every row saved in one batch shares the same value.
Why
Orders sessions chronologically and lets you spot data collected in unusual conditions (late at night, poor light) if accuracy turns out to vary.
How
datetime.now().isoformat(timespec="seconds"), evaluated once per append_dataset() call.
Where
calibration_utils.py → append_dataset()
39schema_version int3
What
Which column layout the row was originally written under. 3 is current; 1 and 2 mark migrated legacy rows.
Why
Older rows only ever had gaze angles and partial position data — the other columns are blank for them. This flag tells training code which rows can support a feature-rich model without having to test every field.
How
Constant SCHEMA_VERSION = 3 for new rows; migrated rows keep the version they were born with.
Where
calibration_utils.py → append_dataset() and _migrate_dataset()

05 Every formula in one place

GAZE ANGLES        deg = Σ(pᵢ × i) × 4 − 180        pᵢ = softmax over 90 bins
                   rad = deg × π / 180

HEAD ROTATION      pitch,yaw,roll = euler_xyz( matrix[:3,:3] )      degrees
HEAD TRANSLATION   tx,ty,tz       = matrix[:3, 3]

IRIS RATIO         x = ((iris − outer)·(inner − outer)) / ‖inner − outer‖²
                   y = (iris_y − midline_y) / ‖inner − outer‖

EAR                (‖p₂−p₆‖ + ‖p₃−p₅‖) / (2 × ‖p₁−p₄‖)

FACE WIDTH         |lm[454].x − lm[234].x|
FACE HEIGHT        |lm[152].y − lm[10].y|

IPD                ‖(lm[473] − lm[468]) ⊙ (W, H)‖₂                  pixels

DISTANCE           focal_px × 6.3 / ipd_px                          centimetres
                   focal_px = 1073.4 measured, or W / (2·tan(HFOV/2))

FACE OFFSET        dx = lm[1].x − 0.5     dy = lm[1].y − 0.5
